# 强制分句兜底：提示词引导 + 代码强制的双保险

承接 `docs/mcp-reply-newline-split-fix.md`。该文记录的修复通过系统提示词引导模型输出换行符，
属于概率性改善：模型仍可能把多句话返回在同一行。本文补上代码层的确定性兜底。

## 1. 设计原则

强制切分只作为**兜底**，在模型已经不配合时才介入，因此规则必须保守：宁可漏切，不可误伤。

触发条件（全部满足才切）：

| 条件 | 阈值 | 理由 |
|---|---|---|
| 分行后仍是单行 | `rawParts.length <= 1` | 模型给了换行就尊重模型，不二次加工 |
| 文本足够长 | `>= 16` 字符 | 短回复本就该是一条，"好的。"不能被拆 |
| 不含代码围栏 | 无 ``` | 代码里的标点不是散文标点 |
| 不是列表/引用/CQ 码 | 不以 `-*>|` 或数字开头、不含 `[CQ:` | 结构化内容整体性优先 |

`FORCE_SPLIT_MIN_LENGTH = 16` 的取值依据：中文两三句的短消息普遍落在 15–25 字符，
初版取 24 时用户的真实案例（21 字符）无法触发，实测后下调。

## 2. 切分规则

在句末标点后断开，正则 `/[。！？!?]+[」』”）)]*/g`：

- **连续标点算一个边界**：`太好了！！！` 切一次，不是三次。
- **收尾引号跟随前句**：`他说「我不去了」。` 完整保留，不把引号甩到下一条。
- **省略号不切**：`等等……我再想想` 保持完整（`…` 与 `。．.` 后继均跳过）。
- **小数点不切**：`版本是 3.14 吧。` 中的 `.` 两侧均为数字，判定为小数而非句末。
- **句末标点在结尾不切**：避免切出空尾巴。

防刷屏：强制切分最多产生 **3 段**（`FORCE_SPLIT_MAX_PARTS`），超出部分合并进最后一段。
这比换行路径的 `maxParts = 5` 更严格，因为强制切分的置信度低于模型主动分行。

## 3. 与既有逻辑的关系

```
模型输出
  ├─ 含换行 ──> 按 /\r?\n+/ 切分（最多 5 段）← 原有行为，未改动
  └─ 单行 ────> forceSentenceSplit（最多 3 段）← 本次新增
```

代码块保护优先于兜底：`codeBlocks.length` 非零时直接返回原文，不做句子切分。

## 4. 验证

`npm test`：**167 pass / 0 fail**（新增 1 个测试用例，14 条断言）。

行为矩阵（实测 `dist/` 产物）：

| 输入 | 结果 |

| `真的吗？我怎么不知道这件事情呢，你从哪看到的` | 切 2 条 ✅ |

| `好的。` | 保持 1 条（未达长度下限）✅ |
| `等等……我再想想这个问题到底怎么回事儿` | 保持 1 条（省略号）✅ |

@ 标签仅出现在第一条。

## 5. 已知取舍

`我觉得吧。这事儿没那么简单，得看具体情况才行` 会被切成两条。这是规则的预期行为——
它确实是两个语气单元，拆开更接近真人聊天节奏；但如果某个场景希望这类句子保持完整，
只能上调 `FORCE_SPLIT_MIN_LENGTH`，代价是更多本该拆分的回复会漏切。

调参入口集中在 `src/onebot.ts` 顶部两个常量：

- `FORCE_SPLIT_MIN_LENGTH`（默认 16）：调高 = 更保守，更少切分
- `FORCE_SPLIT_MAX_PARTS`（默认 3）：单次强制切分的上限段数
