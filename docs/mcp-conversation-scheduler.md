## 默认行为

| 项目 | 行为 |
| --- | --- |
| 合并等待 | 最后一条文字后静默 1500 毫秒再生成，可设 0–3000 毫秒；0 关闭合并 |
| 最长合并时间 | 从一个批次首条文字起最多 5000 毫秒，不因连续输入无限延长 |
| 单批上限 | 最多 20 条、8000 个 JavaScript 字符串长度单位（含换行）；达到限制后后续输入另起批次 |
| 并发 | 默认 3 个独立调度通道，可设 1–5 |
| 调度通道 | 一个私聊好友或一个 QQ 群；同群不同发言人共用发送通道，避免多人回复交叉乱序 |
| 对话记忆 | 私聊按好友；群内直接回复仍按群号 + 发言人，主动接话单独管理 |
| 冷却 | 两次请求开始至少相隔原配置的 cooldown；期间新消息等待，不直接丢弃 |
| 全局请求额度 | 所有会话、直接回复与主动接话共用每分钟上限；暂停不重置额度 |
| 等待队列 | 最多 20 个批次，包含正在合并的批次；已在处理的任务单独计数 |
| 排队超时 | 从批次第一条进入等待队列起超过 60 秒，在模型请求开始前丢弃 |

最长合并时间只是封口期限，不是模型回复时限。封口后的任务仍可能等待同会话前一轮、冷却、并发空位或全局额度；总排队时间仍受 60 秒上限约束。

## 连续输入的处理

1. 同一好友，或同一群内同一个发言人的连续有效文字按接收顺序用换行拼接，作为一条 user 消息发送给模型。
2. 群内必须先由明确 @ 本账号的消息开启合并批次。在该批次仍开放的短窗口内，才允许同一人的不带 @ 补充进入此批次；仍检查白名单、忽略名单、事件时间、自身消息和文字长度。
3. 其他群、其他发言人、带有其他 @、合并窗口结束后的未 @ 消息不获得直接回复资格。主动接话单独沿用既有 opt-in 规则。
4. 模型已经开始生成时，再收到的有效消息进入下一轮，不取消并重发直接回复的模型请求，避免重复计费。
5. 同一调度通道从生成到 QQ 发送完成前一直占用；后续批次开始时读取已经成功完成的前一轮记忆。
6. 批次按首条消息入队次序调度。不同作者的文字不会合为同一批次，记忆也不混用。
7. 超过队列容量的新任务会被明确忽略；合并上限不会静默截断已接收文字。单条非法、过期或超原消息长度限制的事件仍沿用原过滤规则。

## 主动接话、暂停与失败

- 就绪的直接回复优先于尚未开始的主动接话；同一通道不跳过前面等待的批次。
- 同群明确询问会清理旧主动接话候选，并对进行中的主动判断发出取消信号。若提供方忽略取消，仍等该任务实际结束才释放并发槽，迟到结果不会发出。
- 暂停、退出、保存配置或清空记忆取消全部在途模型请求并清理所有合并和排队定时器。
- 暂停后重新开始也不会发送旧运行代次的结果；并发槽仅在旧 promise 实际结束后释放，避免虚假的空闲槽造成超过并发上限。
- 已交给 QQ 的发送不能撤回；模型失败和结果不确定的 QQ 发送不自动重试。
- 请求或发送失败释放自己的通道，其他通道可以继续；失败对话不进入成功回复记忆。

## 代码结构

- `src/scheduler.ts`：独立 ConversationScheduler，负责合并、有限队列、通道互斥、冷却、额度、过期与计时器。时钟可注入，便于确定性测试。
- `src/engine.ts`：消息路由、去重、合并资格判断、模型上下文、主动接话和结果处理；不再只有一个全局控制器。
- `src/config.ts`：新增 mergeWindowMs、maxConcurrent；旧配置缺字段时自动补默认值，并限制范围。
- `src/proactive.ts`：directed 支持注入时间，方便与调度器一致测试。
- `src/main.ts`：推送 activeCount、merging、merged、expired 等状态，保留 active 布尔字段兼容原调用。
- `ui/index.html`、`ui/app.js`：回复规则新增两个配置项；概览与页脚显示实际处理、等待、合并和过期计数。
