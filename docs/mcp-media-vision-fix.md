## 2. 为什么原实现“看不到”

1. **没有真实图像输入。** `ChatMessage.content` 原来只有字符串，模型收到的是 `[图片]`、表情名称或 OCR 文字，没有 `image_url` 图像块。
2. **普通纯图片被路由丢弃。** 没有 OCR 文字时，`route()` 直接返回 null，后续调度与回复都不会发生。
3. **OCR 把 QQ 文件标识当成了文件路径。** 旧代码优先取 `data.file`，再调用 `ocr_image`；实际常见 `file` 是 QQ 的图片标识/文件名，而 OCR 接口要的是可读取的图片路径、URL 或 Base64。
4. **表情名称遮蔽 OCR。** 图片被识别为表情包后会直接进入标签分支，已有的 `ocrText` 被忽略，名称为“动画表情/表情包”时几乎没有语义信息。
5. **读取时机过早。** 旧 OneBot 在白名单和暂停检查前对所有图片调用 OCR，异步预处理还可能让后发的文字先进入 Engine。

当前官方文档确认 `deepseek-flash` 支持图片输入，标准 Chat Completions 使用 `user.content` 的 text/image_url 块，支持 JPEG、PNG、GIF、WebP，图片 Token 与文字一起计费。因此本次不引入另一家服务、不更换模型或 Key。[2](https://api-docs.deepseek.com/guides/vision/)

## 3. 修复后的链路

```text
OneBot 原始事件（保持到达顺序，不抢先 OCR）
    → 原有白名单/黑名单/群参与规则
    → 消息去重、合并、队列、同群串行、限频
    → 获准执行的 Engine.reply
    → 安全解析图片引用 / QQ 图片 CDN 下载 / get_image 解析
    → 开启视觉：真实图像 Base64 + 文字放在当前 user 消息
      关闭视觉：仅 QQ OCR 文字，不向模型上传原图
    → 同一次 DeepSeek chat/completions 请求
    → 原有回复发送、账本和状态更新
```

- QQ 内置 `face` 保留名称映射；`mface`、带 emoji ID 的 image 及数字/字符串 `sub_type=1` 都按表情包处理。
- 表情名称和 OCR 文字同时保留，普通图片也不再静默消失。
- QQ 原始图片 URL 中的 rkey 等参数不放进模型请求；下载成功后只传图像字节。
- 图片块只放在 `user` 消息中。原有系统人设、群聊 JSON 决策规则和文字保持不变；额外说明当前请求是否真的拿到了图像，避免旧人设中的“仅支持文字”错误能力描述或凭标签编造内容。
- 没有额外发起“先描述图片再聊天”的第二次模型请求；正常回复仍是一轮原有模型调用，用量使用 API 实际返回值记录。
- 接通私聊、明确 @、昵称/引用/后续对话以及已经允许的持续群聊/主动候选路径，不扩大白名单。
- 视觉关闭时，无文字的普通图片不会自行开启主动群判断；直接对话、已开启的群会话可尝试 OCR。图片识别不替用户开启主动接话或持续参与。
- 合并批次保留图片引用顺序；超过每批图片数量时另起批次，不把后续图片静默覆盖掉。

## 4. 安全、费用与资源边界

### 明确同意

新增配置 `visionEnabled`，默认 false。主进程 `save-config` 在从关闭改为开启时要求 `confirmVision === true`；不仅是前端弹窗。取消确认不会保存开关，也不会改密钥。

界面明确说明白名单图片将上传到现有 DeepSeek 服务并可能计费。保存配置仍按原逻辑暂停回复，需要显式恢复或按既有启动流程恢复。

### 有界读取

- 每个任务最多 4 张图，单张最多 5 MiB，合计最多 12 MiB；这是应用自己的保护限制，低于服务上限。
- 图片准备总时限 12 秒，媒体 RPC 最多等待 8 秒。暂停/配置变化/断线触发取消，迟到结果不会继续调用模型。
- 限制 Content-Length，同时在流式读取过程中检查实际字节数，不能靠缺少 Content-Length 绕过。
- 校验真实文件头，支持 JPEG、PNG、GIF、WebP，不把 HTML/SVG 或任意文件当图片上传。
- 只允许列明的 QQ 图片 CDN 主机，HTTP 升级为 HTTPS；拒绝 URL 凭据、自定义端口、任意域名、本地 IP、file URL 和重定向。
- 原始消息里的本机路径不会被读取。仅允许 `get_image` 响应给出的本地文件进入后备读取，并经过 realpath 检查，限制在应用托管的 `qq-profile` 内。
- 不会为了识图扫描用户目录，也不会读取私人聊天数据库、聊天导出、浏览器数据或密钥文件。

### 失败与保存

- 下载失败、超时、超限、格式不支持、OCR 无结果时，传递明确的不可识别状态，不把 `[图片]` 或“表情包”标签当成真实画面。
- 媒体错误不回显原始 URL、令牌、文件路径或服务错误正文。
- 图像 Base64 只用于当前模型请求，不写入应用对话历史、日志、用量账本或配置；后续上下文保留原有文字和回答，不重复上传原图。
- QQ/NapCat 自身可能保留下载缓存或运行数据，本修复不承诺整个 QQ 运行栈或云端绝不缓存，也不擅自清理这些数据。
- 动图可以作为 GIF 输入，但不保证模型能理解完整动画时序；不承诺对所有图片都准确识别。
