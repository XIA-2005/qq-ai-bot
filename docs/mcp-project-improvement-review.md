## 一、项目是如何工作的

这是一个 Windows 上的 Electron + TypeScript QQ 助手。桌面主进程 `src/main.ts` 负责应用生命周期、受限 IPC、配置与各服务组装；`ui/` 是桌面界面，`src/preload.ts` 和 `src/ipc-origin.ts` 限制渲染进程可调用的接口。`src/login.ts` 管理内置 NapCat 运行时及扫码/恢复登录，`src/onebot.ts` 通过本机 WebSocket 收发 QQ 事件。

聊天主链路是：**OneBot 事件 → `src/config.ts` 白名单及消息路由 → `src/engine.ts` → `src/scheduler.ts` 合并/队列/限流 → `src/media.ts` 图片或 OCR → `src/model.ts` DeepSeek → `src/onebot.ts` 发消息**。群聊还有持续参与、主动接话、发言后追问与拟人化模块，分别见 `src/group-session.ts`、`src/proactive.ts`、`src/followup.ts`、`src/humanize.ts`。`src/usage-ledger.ts`、`src/api-account.ts` 管理本地费用估算和 API 状态。

远程管理有两条入口：QQ 私聊管理员指令（`src/admin.ts`）和经固定域名/Cloudflare Tunnel 转发到本机 `127.0.0.1:5188` 的移动端 API/PWA（`src/web-server.ts`、`src/remote-access.ts`、`mobile/`）；它们与桌面操作共享 `src/control.ts` 的控制边界。`scripts/`、`package.json` 和根目录启动器负责构建、打包与部署。

**已有良好基础**：主窗口启用沙箱与来源受限 IPC；QQ 与移动 API 默认只监听本机；好友/群白名单、首次发送同意、图片上传单独同意；媒体下载限制 CDN、跳转、尺寸与时限；API Key 使用系统安全存储；费用账本标记未知用量。这些机制应在后续修改中保留，而不是为了便捷绕过。

## 三、优先处理：P1

### P1-1 暂停后仍可能发送尚未交给 QQ 的消息〔已复现〕

**证据**：`src/engine.ts:156-158,194-196` 仅在调用 `send` 前后检查运行代数和取消信号；`src/scheduler.ts:41-45` 暂停时会中止 worker；但 `src/onebot.ts:168-190` 的拟人化等待和逐条发送既不接收也不检查信号。模拟在 `pace` 等待期间暂停，暂停时发送数为 0，随后仍发出 1 条。

**影响**：用户点击暂停、清空或停用对象后，已经生成但仍在“思考/打字”等待中、或者等待下一条气泡的回复可能继续发出。现有“已交付 QQ 的消息无法撤回”提示不能解释**尚未发出**的消息继续发送。

**建议 / 验收**：把 `AbortSignal` 贯穿 `EngineDeps.send`、`OneBot.send`，使用可取消等待，并在每次 `send_private_msg` / `send_group_msg` 前重新检查信号和对象有效性；已经向 QQ 发起且结果不确定的那一条仍不重试。新增“等待首条时暂停”“多气泡之间暂停”“停用对象时暂停”的模拟回归测试，断言不再有后续发送。

### P1-2 群聊“仅 @ / 积极度 0”的告知与实际追问模型调用不一致〔已复现〕

**证据**：`src/engine.ts:105-110,201` 在机器人发言后，对未 @ 的白名单群消息启动 90 秒追问判断，不依赖该群是否开启持续参与或主动接话；`src/followup.ts:13-15,52-73` 的判断会请求模型。纯模拟设置 `engagement=0`、`proactiveEnabled=false`，一次 @ 回复后的一条普通群消息仍使模型调用从 1 次增至 2 次，并可能产生第二条回复。相比之下，`ui/index.html:8,14` 写“默认群内仅被 @ 时回复”；`mobile/app.js:44` 对档位 0 写“不为了判断是否插话而产生费用”。`docs/mcp-followup.md:20-49` 表明追问本身是有意设计，问题在**权限和告知边界**，不能简单视为代码笔误。

**影响**：未 @ 群消息可能产生费用和数据外发，且用户按界面文案会以为它们不参与模型判断。

**建议 / 验收**：明确产品策略：若“仅 @”是严格边界，追问应按群单独选择开启，积极度 0 应停止额外判断；若追问属于默认能力，应在首次同意、群设置、移动端与费用提示中清楚列出范围、90 秒/最多 3 次判断和费用。测试覆盖“仅 @、积极度 0、主动接话关闭、被 @ 后普通消息”的完整链路；在同意策略确定前避免扩大默认范围。

### P1-3 暂停和“清空对话”没有清除追问上下文〔已复现〕

**证据**：`src/engine.ts:50-51` 清除主动接话状态、群房间与常规 `history`，却不调用已有的 `followups.clear()`（`src/followup.ts:48-49`）。模拟显示暂停后窗口仍开放；`engine.clear()` 后 `history=0`，追问窗口仍开放，缓存的机器人发言文本仍有 2 条。

**影响**：短时间内重新开启后，旧窗口可对未 @ 消息继续判断；“清空”并未真正清除这一类模型上下文。

**建议 / 验收**：在暂停/清空语义下清除追问窗口及其文本，明确是否也要清除用于识别引用的 `selfMessages`；分别测试“暂停→恢复”“清空→恢复”“换账号/对象停用”，确保旧上下文不会进入新请求。若有意保留，则 UI 不应称为清空全部对话。

### P1-4 审计写盘失败会造成“操作已生效、调用却报错”〔已复现〕

**证据**：`src/control.ts:31-39,79-88` 先执行配置更改，再同步调用 `hooks.audit`；`src/remote-access.ts:92-96` 的审计会写文件，写盘异常可抛出。模拟注入审计失败后，好友已经加入白名单，但调用抛错，审计又重试失败一次。`src/web-server.ts:190-191` 只在调用成功后缓存幂等响应。

**影响**：磁盘满、权限异常时，桌面/QQ/手机端可能认为操作失败而重试；对修改人设等操作，还可能改变上一个人设备份或产生重复副作用。

**建议 / 验收**：决定审计是否为强一致前置条件：若不是，业务成功应独立返回，审计失败另发告警并保留待写记录；若必须持久审计，则应在变更前验证可写并设计事务/恢复流程。增加“审计写入失败 + 客户端重试 + 操作状态”回归测试，不让审计异常伪装成业务回滚。

### P1-5 打包产物与两个启动入口不一致，升级可能启动旧包

**证据**：`package.json:29-33` 的普通打包输出是 `release-v0.9.0/`；`启动机器人.cmd:5-10` 却只接受被 `.gitignore:7` 排除的 `artifacts/mcp-secure-remote/...`。`scripts/Launcher.cs:24-37` 只要旧 `mcp-secure-remote` 存在就永远优先选它，而不是比较更新的 `release-v*`。`README.md:39-43` 又把 EXE 和 CMD 都作为常规入口。

**影响**：新的源码仓库按 `npm run pack:win` 构建后，CMD 入口仍可能找不到包；已有修复包的机器即使构建更新版本，EXE 入口仍可能运行旧包。

**建议 / 验收**：构建后生成一个受校验的“当前包”清单或统一入口，两个启动器读取同一目标并核对版本/哈希；取消对某个补丁目录的永久硬编码。用隔离的假 EXE 验证“只有新 release”“旧 artifact + 更新 release”“目标缺失”的行为，并在 UI 展示实际运行包的版本与路径。

### P1-6 管理员权限运行的 Cloudflare 安装链需加强来源验证和 Token 处理

**证据**：`scripts/setup-remote-tunnel.ps1:11,51-65` 可从 PATH 选现成可执行文件，或下载 `releases/latest`，随后直接以管理员权限运行；`scripts/install-cloudflare-tunnel.cmd:17-27,33-45,60-61` 还支持把 Tunnel Token 当命令行参数。`docs/mcp-ios-mobile-control.md:83-100`、`一键开启手机远程(免同一网络).cmd:19-27` 仍推荐这一旧式参数入口。新的安全提示入口 `配置iPhone固定远程.cmd:6` 会交给 PowerShell 提示输入，但 `scripts/setup-remote-tunnel.ps1:99` 最终仍把 Token 作为 `cloudflared service install` 的进程参数交给下游程序。

**影响**：管理员环境下执行未固定版本/未验签的二进制属于供应链风险；Token 作为参数可能在命令历史、短时进程信息或系统服务配置中暴露，不应笼统承诺“没有写入项目文件就不会泄露”。

**建议 / 验收**：固定版本，校验发布哈希或 Authenticode 签名，审查 PATH 命中的可执行文件来源；收敛成唯一推荐安装入口，停止在文档中示范命令行传 Token，并检查服务凭证的 ACL 与轮换流程。安装流程在测试中使用替身程序，不用真实管理员权限和真实 Token。

### P1-7 当前工作树需先收敛，才能复现或交付“当前版本”

**证据**：当前 `git status` 为 19 个修改、45 个未跟踪条目，重要新增代码 `src/web-server.ts`、`src/remote-access.ts`、`src/admin.ts`、`mobile/`、`scripts/clean-dist.cjs` 和相关测试尚未纳入当前提交；`artifacts/`、`vendor/`、`release-v*/` 均被忽略。当前测试通过的是这台机器上的**工作树**，不能据此断言别人从 Git HEAD 就能获得同一应用。

**建议 / 验收**：在发布前逐项审阅并提交必要源码、PWA、测试和文档；明确第三方运行时的获取/校验步骤，在干净检出环境执行构建和打包冒烟测试。根目录的 `chat-history.*` 等未跟踪文件仅从文件名看可能涉及聊天记录，**本次没有打开内容**；先由项目所有者确认性质，再定向移出仓库或添加忽略规则，避免误提交，也不要未经确认删除。

## 四、下一阶段：P2

### P2-1 测试数量不少，但关键集成路径仍缺验证

**证据**：覆盖率输出中 `dist/login.js` 行覆盖 **34.98%**、`dist/desktop.js` **61.80%**、`dist/admin.js` **71.92%**，`dist/web-server.js` 分支覆盖 **68.79%**；桌面主要 UI、PWA 和主进程没有纳入这份覆盖率总表。现有 263 项测试通过不能代替真实登录、打包包体和手机浏览器验收。

**建议**：用可控假 NapCat/WebSocket 服务器覆盖扫码状态机、进程退出、恢复、断线与换号；对 PWA 增加浏览器级配对/撤销/错误恢复测试；增加上述暂停发送、追问权限和审计故障测试。真实 QQ、付费 API、安装服务留作经用户确认的手动验收，不接入默认 CI。

### P2-2 文档与代码的“当前状态”不一致

**证据**：`docs/mcp-ios-mobile-control.md:21,147-151,256` 仍说没有 PWA、根地址只是 API 状态页且鉴权仅 Bearer；`src/web-server.ts:13-28,145` 与 `mobile/app.js` 已提供 PWA，并支持设备 Cookie。`docs/mcp-project-overview.md:12,75,145-146` 写固定 3001 端口和 252 项测试，而 `src/login.ts:26-27` 使用随机端口，本次为 263 项。`docs/mcp-version-guide.md:29-40` 把旧表情修复包称为“当前最新版”，`README.md:3-13` 推荐的是后续安全远程包。

**建议**：只保留一个“当前版本/当前入口/运行限制”的权威页；旧实施记录明确标注历史时间与不再适用范围；发布时自动填入版本、入口路径和测试数。尤其先更正移动远程部署手册与 README 的链接说明，以免用户按旧方式操作。

### P2-3 移动 API 的幂等保证目前只覆盖单进程短窗口

**证据**：`src/web-server.ts:64,132-137,190-191` 将写入结果只缓存在内存 `Map` 中，10 分钟后或进程重启即丢失；`src/control.ts:104-111` 对重复设置同一人设仍会更新 `previousPrompt`。`docs/mcp-ios-mobile-control.md:153-159` 对“同一 Key 重试返回首次结果”的表述未交代此限制。

**建议 / 验收**：将重要写操作的键、请求指纹和结果存入有界、过期的持久化日志，或先使操作本身严格幂等（如提示词未变化时不重写备份）；客户端在同一次网络重试复用原键。补“操作成功但响应丢失→进程重启→原 Key 重试”的测试，并明确保证期限。

### P2-4 补齐工程自动化、类型边界与可读性

**证据**：`package.json:9-14` 只有 build/test/启动/打包命令；仓库未发现 CI 工作流、ESLint/Prettier 配置。TypeScript 启用了 `strict`，但 `src/main.ts` IPC 处理器、`src/config.ts:134` 路由、`src/web-server.ts:117-125` JSON 解析和 `src/admin.ts:30` 事件仍以 `any` 穿越输入边界。`ui/app.js`、`ui/index.html` 等文件少量超长物理行，不利于定位改动与代码审查。

**建议**：建立不触碰真实 QQ/付费服务的 CI：锁定 Node 版本，跑 `npm ci`、类型检查、全部测试、关键覆盖率阈值和离线打包资源预检；分阶段引入统一格式化、lint、浏览器脚本类型检查和输入 schema；把主进程装配/IPC/登录/移动端职责拆成可单测模块。避免一次性大规模格式化掩盖行为改动。

### P2-5 从“费用可见”升级到“费用可控”（产品增强）

`src/usage-ledger.ts:51-69` 能在调用后记录估算金额，`src/scheduler.ts:118-123` 能按每分钟请求数节流，但没有独立的**每日/每群费用上限**。可在 UI 提供保守的每日与目标预算、达到阈值提示/暂停新模型请求；对用量未知的请求按风险预留额度，避免误称精确账单。此项属于新增产品能力，不是现有计费功能的正确性缺陷。

## 五、建议实施顺序

1. **先守住用户控制与知情权**：修复 P1-1/P1-3；明确 P1-2 的默认追问授权和费用文案；补三类回归测试。
2. **再修控制可靠性**：隔离审计失败、定义幂等重试边界，补故障注入与重启用例。
3. **发布前收敛**：统一启动器与产物、校验 Cloudflare 安装链、审阅未跟踪文件，在干净检出环境复现构建，更新部署文档。
4. **持续演进**：补关键集成覆盖、CI/类型边界和可选费用预算。
